# E2E Workflow Audit — Validation

**11 Aug 2026 · app build 720 (`cd74f6c`, live on `main`) · live DB `yipslubcptjoarblzbpl`**

Validates the third-party "E2E Workflow Audit" (pasted findings, backend-only) against three
independent sources of truth:

1. **Live database** — table row counts, columns, RLS policies, triggers, applied migrations (read-only).
2. **Source code** — the shipped `index.html` (build 720) and the 26 `api/*.js` functions, swept by a
   7-agent code-wiring pass and spot-verified by direct grep.
3. **A live click-through of the actual UI** — the exact build-720 `index.html` rendered in Chromium and
   driven through the five-step journey the audit asked about (project → estimate → contract → crew →
   payment), recording every write the UI attempted.

**Nothing in production was written.** The click-through runs the real app locally against a mock Supabase
client that reports an admin session and *records* writes instead of sending them; live row counts before
and after are identical (projects 34, estimates 15, inspection_reports 9, contracts 0, crew_work_orders 0,
collections 0, commissions 0, appointments 10). What the click-through proves is **front-end reachability
and the exact intended write payload**; what only the real backend proves (RLS acceptance, trigger effects)
is validated separately against the live schema — which carries the matching tables, columns, triggers and
policies.

## The one-line diagnosis: the audit is a stale snapshot, not a wrong reading

Most of the "critical gaps" are features that **shipped after the audit's data was captured.** The audit
saw **10 crews** (an 11th was added 1 Aug) and **0 punch_items** (the first landed 1 Aug), so its DB
snapshot predates ~1 Aug 2026 — roughly 40+ builds behind build 720. In that window:

- **The whole money system** (`collections` → auto-commission trigger → `draws` → payout board → weekly
  owed email) shipped **9 Aug, builds 650–651**.
- **AI Estimate + the `contracts` / `ai_estimates` tables** shipped **10–11 Aug, builds 715–720**.
- **The Supplement Desk, scope-read history, and code-letters** shipped **9–10 Aug, builds 646–672**.

And because the audit was **backend-only** ("the authenticated UI could not be fully navigated"), it read
empty tables as missing features. On this app that inference is backwards: the tables are empty because
**no one has logged the first real check / dispatched the first crew yet**, not because the software is
absent. Every empty table in the audit is BUILT + WIRED + reachable, verified below by clicking it.

## Finding-by-finding

Legend: ✅ works / built-and-wired · ⚠️ partly true / real but mis-framed · ❌ genuine gap.

### CRITICAL GAPS

**1. Contracts table = 0 rows, no e-sign — ⚠️ half wrong.**
There are **two** contract systems. (a) The **live one**: contract *documents* are HTML rows in
`inspection_reports` (title prefixed "Contract"), generated by "+ New contract" (confirmed in the
click-through — it wrote the row and opened a prefilled Construction Agreement), shared via an
unguessable `share_token` + `/api/share`, and **signed natively** by an in-app signature canvas that
writes `inspection_reports.signed_at` (one signed row already exists in the DB). (b) The **new**
`contracts` + `ai_estimates` tables (builds 715–720): the UI writes `ai_estimates` directly, and the
wired "→ Convert to Contract" button posts to `/api/estimate-to-contract` (correct hyphenated path,
`index.html:24556`), which really inserts a `contracts` row. So "contracts never written" is **false** —
it's unexercised (the AI-estimate flow is a day old). **The genuine gap**: the new tables' downstream
lifecycle is absent — nothing writes `contracts.status` past `draft` or the `sent_at`/`*_signed_at`/
`voided_at`/`signed_pdf_url` columns (dashboards already *read* them), the contract editor's own Sign
button is built-but-unreachable, and there is **no third-party e-sign integration** (signing is 100%
native canvas). Your suggested `sent → viewed → signed → deposit` tracking is a reasonable build **for
the new `contracts` table**; the live `inspection_reports` flow already tracks sent + signed.

**2. crew_work_orders = 0, crews never dispatched, scheduling missing — ⚠️ mostly wrong.**
The build-555 crew Work Order generator is built and wired: "+ New work order" (confirmed reachable in
the click-through) opens a crew/trade picker and `createWorkOrder()` writes **both** the document
(`inspection_reports`) **and** a `crew_work_orders` row (`index.html:18933`). 0 rows = never used, not
broken. Production **scheduling is not missing**: the 14-day Schedule Board is fed by the `appointments`
table (kinds job/drop/appt/team), reachable from the menu, and the Approved-stage flow notifies Curtis
to schedule. **The genuine gap**: the WO *dispatch* lifecycle — nothing writes `sent_via`/`sent_at`/
`completed_on` or moves status past `draft`; "sending" a WO goes through the shared print/editor pipeline
without updating the record. (Also: crews = **11**, not 10.)

**3. Invoicing/collections empty, commissions = 0, no payment tracking — ❌ stale, now wrong.**
A complete money pipeline shipped **9 Aug (650–651)** and is wired end-to-end: the per-job "Money In &
Commissions" tab's **Log Collection** form inserts `collections` (confirmed in the click-through — it
wrote a `$5,000 deposit` row), and the DB trigger `make_commission` then auto-creates the 10% commission
for the job's rep; a standalone payout board (`CardinalPay`, Friday Mark-Paid, pay-net-vs-full draw
settlement, CSV) is reachable; draws and a weekly owed-email cron exist. **0 rows = no check logged yet**
(the triggers were proven live with disposable rows that were deleted). Invoicing exists as a *document
generator* (`createInvoiceFor()` from a signed contract), not a ledger. **QuickBooks is not used
anywhere.** **The one genuine residue**: the app has *two* payment ledgers — `jobFinance()`'s balance math
reads worksheet `paid` amounts from the project's checklist JSON, **not** the `collections` table, so AR
aging and commissions can draw from different stores. That reconciliation is worth a build.

**4. punch_items = 0, no final-walk/callback tracking — ❌ wrong (stale).**
`punch_items` is built and wired (insert/update/delete/comments across three modules; reachable from the
job menu, the profile's Punch Outs tab, and the Production board) and the **DB currently holds 5 live
rows** created 1–10 Aug. Callback tracking is a first-class `kind` value; a "final walk-around" is an
appointment type. The audit's "0 rows" is the pre-1-Aug snapshot.

### MEDIUM

**5. $0 estimates common; require non-zero before "sent" — ⚠️ valid.**
There is **no code guard** requiring `total > 0` before an estimate goes `sent`. The DB pattern (no $0
estimate ever *sent*; 5 of 10 drafts at $0) is user discipline, not enforcement. A guard would **not**
break insurance (money lives claim-side in `insurance_claims`/checklist) or community (bid amount in
`checklist.lead`), and every total-consumer already skips $0. Two caveats before you add a hard DB
constraint: a deliberately discounted-to-$0 estimate is representable, and the post-publish writer can
swallow a refused update while still advancing the stage — so prefer a **client-side confirm** over a
silent DB constraint.

**6. Personal entries mixed with business; add is_business — ⚠️ real, but the fix duplicates an existing convention.**
Appointments carry a 4-value `kind` (appt/job/drop/team). "Hair cut"/"Chase" are `kind='appt'` and render
mixed on the main dashboard calendar — but two filtered mini-calendars already separate **team** and
**production** items. The existing separation axis is `kind`, not a boolean. Cleaner than `is_business`:
add a `personal` (or `misc`) kind, or a personal filter, and reuse the calendar filtering that's already
there.

**7. No inspection checklist table; reps eyeballing — ❌ wrong.**
There's a full ~30-field **Roofing Inspection Checklist** modal (roof + mandatory attic + defects +
overall condition + notes) *and* a separate General Inspection Checklist, both on the profile's Checklists
tab, saved as JSON into `projects.checklist` — and it even auto-generates report findings. The audit found
"no table" because it looked for a dedicated DB table; the data lives in the `checklist` jsonb-in-text
column (confirmed: keys `deckcond`, `ventcond`, `soffit`, `hail`, `wind`, `pitch`, `layers`, `attic`, …).
Low fill rate is adoption, not absence.

**8. No permit / inspection tracker — ✅ CONFIRMED gap.**
Permits exist only as reference-library cards, an expense category, contract boilerplate, and the
`code_letters` register (jurisdiction *building-code-enforcement* letters for insurance supplements — not
municipal permits). There is **no permit status field, table, or tracker anywhere**, and no open-item for
one. This is a real, unbuilt feature.

**9. Empty nav items create confusion; hide until activated — ⚠️ mostly wrong, small kernel.**
Contracts / Work Orders / Commissions are **per-job tabs** (the `jobMenuSel` job menu) that only appear
**when a project is open** — they are not global nav items, and all three are built with working create
buttons and role-aware renderers (confirmed reachable in the click-through). Money surfaces are admin-gated
(crew rates/payments) or RLS-trimmed (a rep sees only their own commission rows). **The kernel of truth**:
the job-tab labels are not role-filtered, so a role that can't act on a tab still sees its (empty) state.
A small role-filter on the tab strip closes that.

### LOW

**10. Photo categorization weak (text-only section) — ⚠️ true only for one narrow surface.**
True for `project_photos.section` (196 rows, all "Inspection"; the upload path never sets it). But
materially wrong for the app overall: inspection-report photos get an **AI sort** into 6 semantic sections
+ severity + trade (`api/sortphotos.js`), the 60K-row CompanyCam mirror has GIN full-text search + tag
filtering, and `studio_photos` carries a `tags[]` chip filter plus a `damage_tags` column. The one
genuinely-missing piece is a UI filter over `studio_photos.damage_tags`.

**11. No automated post-job review request — ⚠️ false for manual/prompted, true for automation.**
`review_left_by`/`review_left_at` are written by the profile's Google-Reviews toggle, and a full
review-request workflow exists (send via SMS/email/clipboard writing `review_requested_at`, an automatic
`confirm()` prompt when a job moves to Completed, and a per-rep asked/got scoreboard). What's absent is a
**server-side/scheduled** automation (a cron that chases reviews without a human tapping).

**12. No executive dashboard — ⚠️ partially valid.**
Retrospective KPIs exist (Graphs & Reports: revenue signed, win rate, open pipeline $), plus a 30-day
Activity Count strip, a daily 11:00 UTC appointment digest email, and a weekly Friday commissions-owed
digest. **Genuinely absent**: a *forward-looking pending-actions rollup* — "N estimates need sending, N
contracts unsigned." Those states exist only per-job (e.g. the "awaiting signature" chip). "Permits
pending" is impossible until permit tracking (#8) exists.

## Your four open questions, answered

- **Is e-sign already built but writing to a different table?** Yes. Signing is a **native in-app
  signature canvas** that writes `inspection_reports.signed_at` (the live contract-document path). There is
  no DocuSign-style integration. The new `contracts` table exists but its `*_signed_at` columns aren't
  written yet — its lifecycle is the real gap (#1).
- **Is production scheduling handled outside the app?** The **Schedule Board is in the app**, fed by the
  `appointments` table; the Approved-stage flow notifies Curtis to schedule. What happens by text/call is
  the *crew dispatch notification* — `crew_work_orders` records the WO but its send lifecycle isn't tracked
  (#2).
- **Are invoices generated in QuickBooks?** No QuickBooks anywhere. Invoices are generated **inside the
  CRM** as a document (`createInvoiceFor()` from a signed contract) — a generator, not a ledger.
- **Should empty tables be hidden from nav?** They aren't nav items — they're per-job tabs that already
  only appear on an open project. The optional refinement is to **role-filter the tab labels** so a role
  that can't use a tab doesn't see its empty state (#9).

## What's actually worth building (the real gaps, ranked)

Everything else the audit flagged is already built. These survived validation as genuine work:

1. **Reconcile the two money ledgers** (#3 residue) — `jobFinance()` reads worksheet `paid` from checklist
   JSON while collections/commissions read the `collections` table, so AR aging and commissions can
   disagree. One shared value function or an on-screen provenance label. *(Highest value — it's live money
   math that can diverge today.)*
2. **The new-contracts lifecycle** (#1) — write `contracts.status`/`sent_at`/`*_signed_at`, wire the
   contract editor's own Sign button, or fold the new tables back onto the proven `inspection_reports`
   signing path. Decide which of the two contract systems is the future before investing.
3. **The crew-WO dispatch lifecycle** (#2) — `sent_via`/`sent_at`/`completed_on` + a status past `draft`,
   so a dispatched crew is visible as dispatched.
4. **Permit / municipal-inspection tracker** (#8) — genuinely absent; a real feature if jobs stall on
   municipal approval.
5. **Forward-looking "needs doing" dashboard** (#12) — a rollup of per-job pending states for Theo.
6. **Smaller:** a non-zero-before-sent confirm on estimates (#5); a `personal`/`misc` appointment kind
   (#6); a `studio_photos.damage_tags` filter UI (#10); a scheduled review-chase cron (#11); role-filter
   the job-tab strip (#9).

## What NOT to "fix" (false alarms — already built and working)

Contracts (both the live document flow and the new tables), crew work orders, the money/commission
pipeline, punch outs, the inspection checklist, native contract signing, production scheduling, photo
AI-categorization, and the review-request workflow are all present and reachable. Their empty tables mean
"no first real transaction yet," not "missing software." Don't rebuild any of them.
